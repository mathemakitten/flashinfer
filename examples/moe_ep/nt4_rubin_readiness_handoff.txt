Research conclusion
-------------------
Keep MegaMoE as a serious Rubin scheduling/communication research vehicle. We now
have a competitive expert-compute implementation and a small matched E2E win at
large batch, so it is no longer justified to assume TRTLLM has an insurmountable
compute advantage. This does NOT prove megakernels are universally optimal or
that more fusion is better. Our competitive configuration deliberately separates
NVLS dispatch/combine and detaches completion/cleanup from large compute CTAs.
The useful design property is coordinated work/readiness scheduling plus timely
resource release, not literally one launch for the entire block.

Current Mega candidate: MXFP8, grouped lookup scheduler, group_hint1024,
152 workers, original fused geometry (no universal narrower-tile adoption),
detached ordinary tail, NVLS hybrid, shortcut overlap. Hardware tanh is a separate
numerical/performance experimental axis. Keep exponential tanh as the control.
Actual CLC did not consistently beat simplified/static lookup on natural routes.
Do not assume CLC, lower worker counts, or finer flags are automatic improvements.

What Rubin should test next
---------------------------
1. Establish an ordinary-readiness Rubin baseline with this scheduling structure,
   fixed activation/precision and route snapshots. Confirm supported compiler,
   cubin architecture and launch resource geometry; do not transplant GB300's
   152-worker choice as a Rubin optimum. Keep a comparable TRTLLM+NVLS baseline.
2. Locate the remaining dependency on a matched per-invocation timeline. Keep
   rank/layer separate. Measure last useful FC2, async drain, compute-CTA exit,
   peer completion, reduction, mixer eligibility/start/completion, and block join.
   Start with layers32/68; analyze layer7 rank skew separately. Existing worker
   results show contention is phase/layer dependent, not a universal occupancy cap.
   Do not add phase medians or infer causal order from static SASS address order.
3. Only where remote readiness is on the critical path, compare ordinary vs
   counted readiness on Rubin with IDENTICAL payload layout, math, reduction,
   staging, CTA geometry and retirement. First use exponential tanh in BOTH arms
   so numerical changes cannot masquerade as a scheduling result. Then replicate
   the winning mechanism with the eventual qualified activation.
4. Test independently delayed sender, delayed local compute, and delayed consumer.
   Distinguish payload visibility, readiness notification, and source-buffer reuse.
   Hardware counters do not automatically make a resident CTA release resources,
   guarantee consumer admission, or establish every required memory-order edge.
5. If the remaining delay is useful compute/resource contention rather than a
   remote wait, prioritize compute-CTA retirement and selective phase/layer
   scheduling. Counted writes cannot remove that contention. Use smaller tasks or
   worker budgets only when join/E2E improves without excessive expert slowdown.
6. Consider Lamport-style per-region readiness only if coarser readiness prevents
   useful work AND there is a supported data-validity contract. Do not infer its
   semantics from a -0 sentinel description alone. Use documented Rubin APIs.

Decision criteria
-----------------
- Matched count notification reduces critical-path join and uninstrumented E2E:
  pursue counted-write integration. Preserve ordinary path as control/fallback.
- Notification becomes earlier but consumers cannot execute: scheduling/admission
  is the next problem; more fine-grained signaling alone is not the solution.
- Detached ordinary tail already hides the wait: no expected win from changing
  notification; move to exposed compute/drain or other measured dependencies.
- Gains appear only in synthetic skew, one layer, or instrumented runs: investigate
  rather than claiming deployment benefit. Require repeated E2E and real routes.
- Neither approach beats TRT end-to-end: keep TRT deployment option; Mega remains
  a research vehicle, not a predetermined winner.

API constraints supplied earlier by the user; agent must verify against actual kit
---------------------------------------------------------------------------------
NVSHMEM counted APIs use existing symmetric heap, not a separate heap. Symmetric
uint64 counter needs256-byte-aligned heap offset; payload and counter reachable
through same counted-capable destination logical endpoint. Pointer-based counted
TMA was described as requiring same FLA page, otherwise demotion may skip update.
Do not conflate that pointer restriction with NVSHMEM offset-based lowering.
Counted fabric put wrappers are not identical to counted UTMASTG/UTMAREDG. Some
counted TMA forms were PTX/internal-only. Obtain exact supported headers, completion
and ordering contract, toolkit and hardware support before coding assumptions.

Current execution model
-----------------------
We are studying NT4 MXFP8 MegaMoE local expert computation with NVLS and shortcut
MoE overlap, including the detached-tail prototype. FC1 writes quantized
activations and scales; FC2's activation loader waits for a token-block readiness
counter, then stages activations through a shared-memory pipeline. These local
FC1-to-FC2 dependencies are distinct from remote dispatch and result-return
readiness. A counter can already be ready while later staging slots remain busy.

Measurement limits
------------------
- Matched recorded inputs; checks confirmed identical input hashes across the
  preceding store-path comparisons.
- Instrumented model branch replay, not uninstrumented end-to-end performance.
- Native CUTLASS outputs continue generation after the measured join. These runs
  therefore do not qualify candidate-driven generation or candidate tokens/sec.
- Existing hardware-tanh FC1 numerical advisory remains in effect. Success here
  is not a new deployment numerical qualification.
- Timing instrumentation perturbs execution. FC1 flag bookkeeping may defer
  publication; its interval is not a precise counter-completion timestamp.
- First/last TMA ISSUE markers are not transfer-COMPLETION markers.
- Large median waits alone cannot identify the block's critical path. Preserve
  rank, layer, invocation, CTA and dependency identity when reconstructing it.

Running experiment: FC2 producer next-slot probe order
-----------------------------------------------------
The activation producer currently probes the next shared-memory staging slot
before issuing the current tile's activation+scale TMA transfers. We are testing
moving that probe AFTER the current transfers. Hypothesis: a waiting next-slot
probe can delay useful current transfers. This is a hypothesis, not an established
explanation; the precise try_acquire behavior and measured outcome matter.

Private flag: NT4_FC2_PROBE_AFTER_ISSUE=1 (default 0).
Math, readiness waits, pipeline acquire/release operations and tile geometry stay
unchanged. The flag is in the private compile key and restricted to NT4.

Each node runs:
- Four rank-local routing-distribution qualifications, with exact FC1 bytes/scales
  and output checks, poisoned intermediates, eager/graph replay, repeated poison.
- 24 coarse model comparisons: two repetitions x two worker counts x two schedules
  x control-start/candidate/control-end.
- Four separate internally instrumented comparisons at the primary worker count.

--------------------------
1. Identify a specific remote dependency: dispatch payload arrival -> expert
   consumption, or expert-result arrival -> combine/tail consumption. The mixer
   core may already be eligible independently; do not assume it should wait on
   expert completion. Distinguish mixer core, post-processing/shared-expert tail,
   result reduction and final join.

Rubin API constraints previously supplied by the user (verify against actual
headers/toolchain before implementing; these GB300 experiments do not validate
these API contracts):
- NVSHMEM counted APIs use the existing symmetric heap, not a separate heap.
- signal_addr is a symmetric uint64_t counter with a 256-byte-aligned heap offset.
- Payload and counter must be reachable through the same counted-capable logical
  destination endpoint. Heap membership alone does not establish eligibility.
- Pointer-based counted writes have a same-FLA-page condition; do not conflate
  their rules with endpoint-offset fabric operations or TMA counted forms.
- Counted TMA wrappers may require Rubin-specific/PTX-level support. A normal TMA
  C++ wrapper does not imply counted support. Do not invent a public API.
