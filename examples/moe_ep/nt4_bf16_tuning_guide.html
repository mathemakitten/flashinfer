01 / OVERVIEW

What group_hint changes

group_hint sets a target number of FC1 cluster tiles in an expert group. The scheduler places the group’s FC1 work before that group’s FC2 work.

Scope: this guide describes our NT4 BF16 direct path. The dispatch, FC1, activation, FC2, and return work are integrated into the main megakernel. Final weighted reduction is a separate kernel. The NVLS hybrid and MXFP8 implementations have additional differences.

All matrix widths here are the 768-wide routed-expert latent representation, not NT4’s 3072-wide model residual stream. Mixer, shortcut orchestration, shared experts, and surrounding model operations are outside this diagram.

The hint is part of the compilation key. A new value creates a kernel specialization; cached specializations can be reused. The experts in each group are still determined at runtime from the current routing counts.

Default hint

152 SMs ÷ 2 CTAs/cluster = 76

The launcher uses max_active_clusters when the hint is unspecified.

Tuned hint

group_hint = 512 or 1024

The hint changes grouping. The persistent grid is calculated separately. It does not launch 1024 clusters.

03 / TILE GEOMETRY

FC1 and FC2 tile dimensions

For an expert with T routed token rows:
    B = ceil(T / 256)
    FC1 cluster tiles = B × ceil(4096 / 256) = B × 16
    FC2 cluster tiles = B × ceil( 768 / 256) = B ×  3

FC2 has fewer output tiles, but each tile runs a longer K loop. A tile count is therefore a scheduling unit, not an equal-time unit across FC1 and FC2.

04 / INTERACTIVE EXAMPLE

How experts are grouped

The scheduler walks consecutive local experts until their combined FC1 tile count reaches the hint. It includes whole experts, so the count can exceed the target. Zero-token experts add no tiles.

These are synthetic examples of scheduler input counts, not captured benchmark routes. Changing the example does not simulate latency.

FC1 tile-index intervalFC2 tile-index interval
GroupLocal expert IDsNonempty expertsFC1 tilesFC2 tiles
while experts_remain and group_fc1_tiles < group_hint:
    B = ceil(expert_token_count[expert] / 256)
    group_fc1_tiles += B * 16
    group_fc2_tiles += B * 3
    expert += 1

sequence += [all FC1 tiles in this group,
             all FC2 tiles in this group]
This is an index ordering, not a global execution barrier. Independent clusters can be at different positions. FC2 readiness is enforced by counters, not by assuming all earlier tiles have completed.
05 / PERSISTENT EXECUTION

Static assignment to persistent clusters

In the static scheduling mode used by our finalists, each cluster repeatedly takes its own indices from the logical sequence:

tile_index = cluster_id
while tile_index < total_tiles:
    execute(decode(tile_index))
    tile_index += num_persistent_clusters

First 16 assigned indices, assuming a 76-cluster grid. Uses the group hint and routing example above. Color denotes phase, not duration.

Decode an assigned index

Within an expert’s phase interval, let local_id be its tile index:

PhaseToken blockOutput-channel tile
FC1local_id // 16local_id % 16
FC2local_id // 3local_id % 3

The scheduler adds expert/workspace offsets and validity information, then maps the cluster token block to the two CTA row regions. The published descriptor includes phase, expert, tile coordinates, valid rows, and workspace/counter offsets.

How the atomic candidate differs

Instead of taking fixed-stride indices, a leader CTA obtains the next index from a global atomic counter and broadcasts it within its cluster. Grouping still defines the FC1/FC2 index sequence. Atomic scheduling was tested, but was not one of the two fastest candidates.

Each FC1 channel tile contributes part of the 4096-wide intermediate. FC2 must not load that intermediate until all required contributions are published.

This slider illustrates one token block. It does not model the temporal order of stores or batched counter publications.

FC1 producer epilogue

  1. Apply activation and cast to BF16.
  2. Write the intermediate to the FC1 workspace.
  3. Drain the store pipeline and perform memory ordering.
  4. Publish completion with the counter protocol.

FC2 activation loader · warp 5

  1. Locate the expert/token-block counter.
  2. Spin until it reaches 32.
  3. Perform an acquire load and async-proxy fences.
  4. TMA-load the BF16 intermediate into shared memory.

Warp 6 loads FC2 weights independently: the weights do not depend on FC1. Once operands are ready, warp 4 issues FC2 MMA work, and the epilogue handles the result. This handoff uses explicit counters; it is not the proposed Rubin counted-write path.

08 / WHERE VALUES LIVE

Where operands and intermediate results are stored

FC1’s output still goes through global memory. We write the intermediate to a workspace and reload it for FC2, even though both GEMMs execute in the same kernel.

Inside an epilogue thread

// Logical source-level fragment, not physical register numbering:
FP32 accumulator_fragment[32] = load_from_TMEM(...)
for each element z:
    z = max(z, 0)
    c = 16 * tanh(z / 16)
    activation = c * c
    output = BF16(activation)

The source uses a tcgen05 TMEM-load operation and a 32-element FP32 register tensor for the current subtile. Routing weights are applied after FC2. Inherited names such as r_gate and swiglu remain in the code, but this NT4 path performs nongated clamped squared ReLU.

WorkerLogical thread-local state
SchedulerGroup boundaries, expert index, work index, phase, offsets, valid-row counts
TMA loadersAddresses/descriptors, pipeline stage/phase, coordinates, readiness values
MMA issuerOperand descriptors, TMEM address, K-loop and accumulation-control state

BF16 uses two accumulator stages totaling 512 TMEM columns. This is a TMEM allocation, not 512 ordinary registers per thread.

Physical register counts remain unmeasured here. Logical register tensors do not translate one-for-one into additional physical registers. Compiler liveness, reuse, lowering, and spills determine the result. Exact registers/thread and SASS R… assignments require the compiled specialization’s resource report and disassembly.
09 / TUNING RESULTS

Isolated results for group512 and group1024

We reran group512 and group1024 against the default BF16 MegaMoE configuration on GB300. We used captured routing at 128 and 256 requests, three layers, and two samples per layer. Both candidates passed the current correctness checks before timing.

CandidateMedian per-sample speedupWorst sample speedup
group5121.947×1.656×
group10241.934×1.723×

Maximum bracketing-control drift: 0.0434%. Ratios compare each sample with its faster unchanged control. Measurements include capacity clearing/staging, the megakernel, and final weighted reduction. They use graph replay and the maximum per-rank GPU-event duration. They are not vLLM comparisons or full-model speedups.

Why a larger group could help

What changes in the code
  • Longer FC1 intervals before each group’s FC2 interval.
  • Different tile-to-cluster assignment.
  • Fewer group-level phase alternations.
  • Unchanged tile geometry, warp roles, and arithmetic.
Possible reasons for the speedup
  • Less time waiting for FC1 completion.
  • Better distribution of short-K FC1 and long-K FC2 work.
  • Different weight/intermediate locality.
  • Reduced pipeline disruption at phase transitions.

We haven’t yet measured which of these explains the speedup. Nsight Systems can show kernel boundaries and staging/reduction costs. To separate waiting from compute inside the megakernel, we need instrumentation or Nsight Compute analysis.

Current E2E reference point

Before this BF16 scheduling change, the five-round BF16/128 stability run measured MegaMoE at 1217 output tokens/s, vLLM + NVLS at 1249, and FlashInfer controls at 1258/1247. MegaMoE was roughly 3% slower. The isolated tuning gain has not yet been confirmed E2E. Output quality equivalence is also unresolved; numerical checks and exact-sequence comparisons do not establish task accuracy.

10 / TUNING PROCEDURE

How we’re testing the configurations

  1. Capture real inputs and routing. BF16 weights, routed inputs, IDs, probabilities and baseline outputs at both 128 and 256 requests; layers 7/32/68; two full-occupancy decode samples each.
  2. Profile the unchanged path. Separate profiling from timing. Inspect the main kernel, staging and final reduction; then investigate internal stalls if needed.
  3. Try the scheduling knobs. Work grouping, static/atomic assignment, readiness flag batching and epilogue flag batching. Keep arithmetic and geometry fixed.
  4. Check correctness on every sample. Independent BF16 reference, expert contributions, weighted recombination, live baseline, poisoned-buffer replay, graph/eager agreement.
  5. Run the default configuration before and after. We only select a candidate automatically if control drift is at most 3% and every sample improves by at least 2%. These are practical cutoffs; they don’t establish statistical significance.
  6. Confirm E2E. Compare unchanged and tuned MegaMoE, vLLM + NVLS, and initial/final FlashInfer controls in one stable experiment. Keep occupancy and token budget matched.
We’re taking group1024 into E2E testing because it did better on the worst sample. Group512 had a slightly higher median. We still need to see whether either helps full-model throughput.

Operations checklist
  • Use an otherwise idle node; record telemetry and source revision.
  • Do not sync edits into a running experiment.
  • Keep JIT caches and real captures on persistent storage.
  • Independent private graph pools are the current policy. The attempted shared-pool path failed cross-bucket checks and was withdrawn.
  • Resumed trials are useful exploration; repeat finalists with fresh controls in one session.
  • Do not interpret padded buffer capacity as actual active-token count.

Glossary

CTA: CUDA thread block. Cluster: cooperating group of CTAs. Warp: 32 threads. TMA: hardware-managed tensor data transfer. TMEM: tensor memory used by the tensor-core accumulator path. Epilogue: processing/storage after GEMM accumulation. Persistent kernel: workers execute multiple assigned tiles before exiting. Group: consecutive experts used to define an FC1 interval followed by an FC2 interval.
